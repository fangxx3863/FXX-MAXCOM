## 1. 需求细化

### 1.1 核心传输层

| 需求 | 优先级 | 说明 |
|------|--------|------|
| 串口 (Serial COM) | P0 | 全功能：波特率/数据位/停止位/校验位/流控，支持虚拟串口 |
| TCP Client/Server | P0 | 支持长连接、自动重连 |
| UDP Client/Server | P0 | 支持广播、组播 |

**端口管理特性：**
- 显示串口号 + 设备描述符名称（如 `COM3 - Silicon Labs CP210x`）
- 用户可设置**自定义别名**，持久化保存
- **记忆每个端口的上次配置**（波特率等），再次打开自动恢复
- **端口黑名单/隐藏**功能：屏蔽蓝牙串口等不需要的设备
- 热插拔检测：设备插拔自动刷新列表；正在使用的端口断开则触发自动重连

### 1.2 双模式显示系统 ⭐ 核心设计

MAXCOM 同时提供两种显示模式，通过**侧边栏菜单切换页面**（不是同屏分屏），同一时刻只显示一种模式。切换过程不中断串口连接——两种模式的缓冲区在后台同时运行。

#### 模式切换：侧边导航菜单

```
┌──────────┬──────────────────────────────────────────┐
│  📡 端口  │                                          │
│  💻 终端  │  ← 当前选中                              │
│  📋 收发  │                                          │
│  📊 绘图  │       当前页面的内容                       │
│  📈 统计  │                                          │
│  ⚙ 设置  │                                          │
│          │                                          │
│  COM3 ●  │                                          │
│  115200  │                                          │
└──────────┴──────────────────────────────────────────┘
```

- 左侧垂直导航栏（图标 + 文字），右侧为当前页面内容区
- 点击导航项即时切换页面，串口连接保持不断
- 底部显示当前连接状态（端口、波特率、连接指示灯）
- 导航栏宽度可拖拽调整，可折叠为仅图标模式

#### 模式 A：交互式终端页面


**特性：**
- 完整 ANSI 转义序列渲染（核心子集），包括光标移动、清屏、颜色
- **击键直传**：每次按键直接发送到串口（默认不回显，由远端控制）
- **本地回显（Local Echo）开关 ✅ 新增**：远端不回显时，可开启在本地同步显示输入字符（行编辑 + 退格/回车处理），避免用户看不到自己打了什么
- 支持 Ctrl+C (0x03)、Ctrl+D (0x04)、Ctrl+Z (0x1A) 等控制字符
- 支持方向键（转义序列）、Tab 补全
- 支持鼠标选中文本 → 复制到剪贴板（不发送）
- 支持粘贴文本（逐字符发送或批量发送，可配置间隔）
- 回滚缓冲区：可向上滚动查看历史输出，不影响当前终端状态
- **原地刷新**：利用 ANSI 滚动区域 + 光标移动实现"原地更新"，避免滚屏闪烁

#### 模式 B：传统收发分离模式 (Log View + Send Panel)

**适用场景**：协议调试、AT 指令测试、日志分析、长时间数据采集

**特性：**
- **智能时间戳**：基于空闲超时分包（可配置 10ms~500ms），避免 printf 被截断
- **日志等级过滤**：自定义正则规则（如 `\[D\]` `\[I\]` `\[W\]` `\[E\]`），可单独开关
- 日志行颜色按等级渲染（ANSI 颜色仅在此处做简化映射，不解析全部序列）
- 接收区可暂停滚动、搜索、导出为文件（带时间戳）
- 发送区：文本/Hex 切换，编码选择（UTF-8/GBK/Latin-1），换行符配置
- 右侧可展开命令列表面板，支持分组、快捷键、变量替换

#### 模式切换机制（各引擎独立解析原始流）✅

> **核心原则 ✅**：事件总线对每个消费方分发**同一份原始字节流**。时间戳分包、ANSI 解析、绘图帧解析、文件落盘各自在独立的后台 Worker 里处理自己订阅的那份流——**解析互不耦合、互不阻塞、互不修改原始流**。

```
                 ┌──────────────────────┐
                 │   Transport (I/O线程)  │
                 │      原始字节流 raw     │
                 └──────────┬───────────┘
                            │ fan-out（同一份原始流，未做任何处理）
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
┌────────────────┐  ┌────────────────┐  ┌────────────────┐
│ 终端解析 Worker  │  │ 日志解析 Worker  │  │ 其他消费方      │
│ (后台线程)       │  │ (后台线程)       │  │ ·绘图帧解析     │
│ ·ANSI 解析      │  │ ·智能分包+时间戳  │  │ ·文件落盘      │
│ ·屏幕缓冲区      │  │ ·自动染色        │  │ ·统计/FFT     │
│ ·染色(让位)      │  │ ·过滤           │  │  各自独立处理   │
└───────┬────────┘  └───────┬────────┘  └──────┬─────────┘
        │                   │                   │
        ▼                   ▼                   ▼
┌────────────────┐  ┌────────────────┐  ┌────────────────┐
│ 交互终端         │  │ 传统收发         │  │ 绘图/日志/文件   │
│ Viewport (GUI)  │  │ Viewport (GUI)  │  │ Viewport (GUI) │
└────────────────┘  └────────────────┘  └────────────────┘
```

- **谁需要什么格式，谁自己解析**：终端要 ANSI 解析，日志要时间戳分包，绘图要二进制帧解析，文件要原始+时间戳——各消费方各取所需，互不干扰
- **时间戳分包是日志/文件路径的本地行为**，不作用于原始流本身；绘图端订阅原始流，永远拿得到完整二进制帧，不受分包截断影响
- 各解析管道互不耦合：改动一个引擎不影响其他引擎，也便于逐个独立测试
- 切换页面只是切换 GUI 显示哪个 Viewport，后台所有管道持续运行、持续解析，切换无加载延迟
- 发送数据**始终走同一条发送路径**：交互模式下击键直传，传统模式下从发送框发送——发送不影响接收管道

### 1.3 ANSI 解析引擎

> **决策 ✅**：实现核心子集（SGR + 光标移动 + 滚动区域 + 清屏），覆盖 90% 实际使用场景。不追求完整 VT100/xterm 兼容。

| 需求 | 优先级 | 说明 |
|------|--------|------|
| SGR 图形渲染 | P0 | 16色 + 256色 + 真彩色(24-bit)、粗体、斜体、下划线、删除线、反色 |
| 光标移动 | P0 | 上下左右、行列定位、保存/恢复位置 |
| 清屏/清除行 | P0 | ED(Erase in Display)、EL(Erase in Line) |
| 滚动区域 | P0 | 设置滚动区域 + 上滚/下滚 → "原地刷新"不滚屏 |
| 插入/删除行 | P1 | IL(Insert Line)、DL(Delete Line) |
| 删除/插入字符 | P1 | DCH(Delete Character)、ECH(Erase Character) |
| OSC 序列 | P2 | 窗口标题变更等（按需） |
| DCS/SOS/PM/APC | — | 不实现，静默跳过 |

**遇到不支持的序列 → 记录日志 + 静默跳过，绝不崩溃。**

### 1.4 自动染色系统 ⭐

> **定位**：ANSI 解析器的**互补功能**。当数据流不含 ANSI 颜色代码时（多数裸机/RTOS 场景），由自动染色引擎接管，按预设规则给日志行着色。当检测到 ANSI 序列时自动让位，不叠加处理。

#### 核心设计原则

```
每行数据到达 →
  ├─ 包含 ANSI Escape 序列（\x1b[）？
  │   YES → 交给 ANSI 解析器全权处理，自动染色**不插手**
  │   NO  → 进入自动染色规则链
  │
  └─ 自动染色规则链（按优先级，首次匹配生效）：
      1. 日志等级括号规则  [D] [I] [W] [E] [F] → 整行染色
      2. 日志等级关键词规则  DEBUG INFO WARN ERROR FATAL → 整行染色
      3. 键值对规则  "KEY: VALUE" → 冒号后内容染色
      4. 用户自定义正则规则 → 匹配部分染色
      5. 无匹配 → 默认色
```

**为什么需要这个？**

| 场景 | 数据特征 | 处理方式 |
|------|---------|---------|
| Zephyr RTOS 日志 | 自带 ANSI `\x1b[31m[ERR]\x1b[0m ...` | ANSI 解析器处理，自动染色**跳过** |
| STM32 裸机 printf | `[E] Sensor error: 0x05` | 无 ANSI → 规则1匹配 `[E]` → 整行红色 |
| ESP32 调试输出 | `I (342) wifi: connected` | 无 ANSI → 规则2匹配关键字 `wifi:` → 键值对染色 |
| 用户自定义协议 | `CH1: 23.5, CH2: 18.2` | 无 ANSI → 规则3匹配冒号 → 数值高亮 |

#### 全局开关

| 开关 | 说明 |
|------|------|
| 自动染色总开关 | ON/OFF，关闭后所有日志行使用默认前景色 |
| ANSI 检测开关 | ON：遇到 ANSI 序列自动让位 / OFF：即使有 ANSI 也强制应用规则 |
| 每条规则独立开关 | 可单独启用/禁用，例如只开 `[E]` 红色高亮 |

#### 内置规则

**规则1：日志等级括号**

```
匹配: [D] [DEBUG] [I] [INFO] [W] [WARN] [WARNING] [E] [ERR] [ERROR] [F] [FATAL] [CRITICAL]
行为: 整行按等级染色
颜色: D=灰, I=白/默认, W=黄, E=红, F=红+粗体
```

**规则2：日志等级关键词**

```
匹配: 行首或空格后的 DEBUG: INFO: WARN: WARNING: ERROR: ERR: FATAL: CRITICAL: 
      以及 <D> <I> <W> <E> <F> 尖括号变体
行为: 整行按等级染色
```

**规则3：键值对冒号**

```
匹配: "KEY: VALUE" 模式
行为: 冒号后的 VALUE 部分使用强调色
示例: "temp: 23.5" → "temp:" 默认色, " 23.5" 高亮
      "addr: 0x2000_1000" → 数字部分额外高亮
```

**规则4：数值高亮（内置辅助规则）**

```
匹配: 0x[0-9A-Fa-f]+ (十六进制) / \d+\.\d+ (浮点) / \d+ (整数)
行为: 数字使用区分色
```

#### 用户自定义规则

```toml
# 在全局配置或项目 filters.toml 中定义
[[color_rules]]
name = "CAN ID 高亮"
pattern = "CAN[0-9]+:"       # 正则
target = "line"              # "line" = 整行 | "match" = 仅匹配部分
color = "#FF9500"            # 前景色
bg_color = ""                # 背景色（可选）
bold = false
enabled = true
priority = 10                # 越小越优先（内置规则：level=1, keyword=2, kv=3, number=4）

[[color_rules]]
name = "自定义温度"
pattern = "MCU_TEMP:\\s*"
target = "match"
color = "#00FFFF"
enabled = true
priority = 5                 # 比内置键值对规则优先级高
```

#### 与过滤引擎的关系

```
数据到达 → 自动染色（颜色标签） → 过滤引擎（显示/隐藏） → 渲染
           │                      │
           │ 先染色                │ 后过滤
           │ 被过滤掉的行仍          │ 颜色标签已附加，
           │ 会染色                 │ 过滤不影响颜色
```

> 过滤行是否**写入文件**待确认，见 §11 O2。

### 1.5 时间戳系统（= 智能分包）

> 时间戳的精度依赖于**空闲分包**机制。两者是同一件事：按空闲超时切分数据帧，每帧一个时间戳。这个功能有**独立开关**。
>
> **归属边界 ✅**：智能分包是**日志/文件路径的本地行为**。事件总线对日志 Worker 分发的仍是原始字节流，分包在日志 Worker 内部完成——绘图、终端等消费方拿到的始终是未分包的原始流，互不影响。

| 需求 | 优先级 | 说明 |
|------|--------|------|
| 智能分包开关 | P0 | ✅ **全局开关**，关闭后所有数据视为一个连续流，不加时间戳（或按行加） |
| 空闲超时配置 | P0 | 可配置空闲时间（10ms~500ms），超时后新数据视为新帧 |
| 时间戳格式可选 | P0 | 绝对时间 `HH:MM:SS.ms` / 相对时间 `+ms` / 差值 `Δms` |
| 时间戳与数据绑定存储 | P0 | 保存到文件时一并写入 |
| 帧模式 vs 行模式 | P0 | 按空闲分包 vs 按 `\r\n` 行分割 |

**智能分包逻辑（开关打开时，仅在日志/文件路径内生效）：**
```
数据到达 → 追加到当前帧缓冲区 → 重置空闲计时器
空闲超时触发 → 当前帧封包 → 附加时间戳 → 分发到显示/文件/绘图
新数据到达 → 开始新帧
```

**开关关闭时：**
```
数据到达 → 直接透传，不封包不加时间戳（或仅按行加简单时间戳）
```

**使用场景：**
- 开关 **开**：调试协议、分析时序，printf 不被 USB 包边界截断
- 开关 **关**：纯终端交互模式，或调试板自己已经很好地管理了输出时序

### 1.7 数据可视化/绘图引擎

借鉴 SerialPlot 的优秀设计并超越它。

| 类别 | 需求 | 优先级 | 说明 |
|------|------|--------|------|
| **数据格式** | Simple Binary | P0 | 设置通道数、数据类型(int8~int64, float32/64)、端序 |

- 换行符是**发送端**的可配置项：调试 AT 指令需要 `\r\n`，调试协议可能需要裸数据不带换行
- 发送框要能显示转义字符（`\r` `\n` 等），方便精确控制发送内容

- 这是"板子自己管理输出时序"场景下的关键——不依赖分包，只靠 `\r\n` 分行

## 3. 技术选型（已确认）

### 3.1 GUI 框架：DearPyGui ✅

| 理由 | 说明 |
|------|------|
| GPU 加速渲染 | 高频实时数据刷新（终端日志 + 波形图）的核心保障 |
| 内置 Plot API | 省去第三方绘图库集成 |
| 打包体积小 | Nuitka 编译后 < 30MB |
| 控件不足 | 通过自定义 `draw_text` + `draw_rect` 逐行绘制控件弥补 |

**风险应对：**
- 中文字体 → 选用 Sarasa Gothic（更纱黑体）等宽字体
- 复杂布局 → 自研布局管理器封装
- 大量文本性能 → 虚拟化渲染（只渲染可见行）

### 3.2 包管理：uv ✅

使用 [`uv`](https://github.com/astral-sh/uv) 管理 Python 依赖和虚拟环境：
- `uv pip install` 替代 pip（快 10-100x）
- `uv sync` 从 `pyproject.toml` 同步依赖
- 全局锁文件 `uv.lock` 保证 CI 和开发者环境一致

### 3.3 语言：纯 Python 3.13 ✅

**Python 3.13**（标准构建，带 GIL）。3.13 带来了显著的解释器性能提升（更快的字节码、新的指令集、改进了的字符串/列表操作），对 ANSI 解析、字符串处理和行缓冲这类 CPU 密集路径帮助明显。

> ⚠️ **不使用** 3.13 的 free-threading 实验模式（`--disable-gil`）——DearPyGui 这类 C 扩展对无 GIL 构建兼容性风险大，收益不确定。

关键路径用 C/Rust 优化：
- ANSI 解析：纯 Python 状态机，3.13 下吞吐更高
- FFT：`numpy` + `scipy`（底层 C/Fortran）
- 串口 I/O：`pyserial`，必要时用 `ctypes` 调 Win32 API
- 绘图渲染：DearPyGui 本身就是 C++

### 4.1 ANSI 解析引擎

**状态机设计：**

```

                          │          GROUND               │
                          │  (普通文本 / 打印字符)         │
                          └──┬──┬───┬───┬──────┬─────────┘
                             │  │   │   │      │
                  0x1B (ESC) │  │   │   │      │ 0x9B (CSI 8-bit)
                             ▼  │   │   │      ▼
                    ┌──────────┐│   │   │  ┌──────────┐
                    │  ESCAPE   ││   │   │  │CSI_ENTRY │
                    └──┬───┬───┘│   │   │  └────┬─────┘
                       │   │    │   │   │       │
             0x5B '[' │   │0x5D│   │   │       │ 0x30-0x3F
                       ▼   │    │   │   │       ▼
                 CSI_ENTRY  │    │   │   │  ┌──────────┐
                    │       │    │   │   │  │CSI_PARAM │
                    │       │    │   │   │  └────┬─────┘
        0x30-0x3F  │  0x5D ▼    │   │   │       │ 0x20-0x2F
                    │  ┌───────┐│   │   │       ▼
                    ▼  │OSC_STR││   │   │  ┌──────────┐
               CSI_PARAM │     ││   │   │  │ CSI_IGM   │ (intermediate)
                    │    │     ││   │   │  └────┬─────┘
                    │    │     ││   │   │       │ 0x40-0x7E (final byte)
                    │    │     ││   │   │       ▼
                    │    │     ││   │   │  ┌──────────┐
                    │    │     ││   │   │  │ DISPATCH  │ → 执行动作
                    │    │     ││   │   │  └──────────┘
                    ▼    ▼     ││   │   │
                (回到GROUND)   ││   │   │
                               ││   │   │
              其他 ESC 起始字符: │   │   │
              ESC 7/8 (DECSC/DECRC) → DISPATCH
              ESC M (RI, 反向换行)    → DISPATCH
              ESC D (IND, 换行)       → DISPATCH
              ESC E (NEL, 换行+回车)  → DISPATCH
              ESC c (RIS, 硬重置)     → DISPATCH
```

### 4.3 绘图引擎

**管道架构（绘图订阅原始字节流，不受智能分包影响）：**
```
原始字节流（来自事件总线，未分包）
    │
    ▼
┌────────────┐    ┌──────────────┐    ┌─────────────┐
│ DataSource │ →  │ FrameParser  │ →  │ChannelSplit │
│ (RingBuf)  │    │ (协议解析)    │    │ (通道分离)   │
└────────────┘    └──────────────┘    └──────┬──────┘
                                             │
              ┌──────────────────────────────┼──────────────────┐
              ▼                              ▼                   ▼
       ┌─────────────┐               ┌─────────────┐    ┌──────────────┐
       │  Waveform   │               │  Bar Chart  │    │  Statistics   │
       │  Renderer   │               │  Renderer   │    │  Processor    │
       └──────┬──────┘               └──────┬──────┘    └──────┬───────┘
              │                              │                   │
              ▼                              ▼                   ▼
       ┌─────────────────────────────────────────────────────────────┐
       │                  DearPyGui Plot / DrawList API               │
       └─────────────────────────────────────────────────────────────┘
```

**FrameParser 数据对齐机制（借鉴 SerialPlot，作用于绘图解析器的本地游标）：**
```
绘图 Worker 订阅原始字节流（未经分包处理），维护自己的解析游标。
当发现数据错位时:
  用户点击 [跳过1字节] → 只推进绘图解析器的本地游标（丢弃首字节，不写回原始流）
  → 重新尝试解析帧头 → 重复直到帧头对齐 → 后续自动同步

关键约束: 跳过字节只改变绘图解析器自己的状态，
          绝不影响终端/日志/文件等消费方拿到的原始数据。
```

**FFT 管道：**
```
RingBuffer → 取窗口(N=1024~65536) → 加窗(Hann/Hamming/Blackman/None)
           → numpy.fft.rfft → 幅度谱(dB) + 相位谱 → Plot
```

## 5. 数据流与线程模型

### 5.1 核心原则：单一原始流 + 独立解析引擎 ✅

> **决策 ✅**：事件总线把**同一份原始字节流**扇出给每个消费方；各引擎（终端/日志/绘图/文件）在自己独立的后台线程里解析各自订阅的那份流。**解析互不耦合、互不阻塞、互不修改原始流。**

```
                 ┌──────────────────────────────┐
                 │  Transport (I/O 线程)          │
                 │  原始字节流 raw (未处理)         │
                 └──────────────┬───────────────┘
                                │ 事件总线 fan-out（同一份原始流）
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
┌───────────────┐      ┌────────────────┐      ┌────────────────┐
│ 终端引擎 (线程) │      │ 日志引擎 (线程)  │      │ 绘图引擎 (线程)  │
│ ·ANSI 解析    │      │ ·智能分包+时间戳 │      │ ·帧解析         │
│ ·屏幕缓冲区    │      │ ·自动染色       │      │ ·通道分离       │
│ ·染色(让位)    │      │ ·过滤          │      │ ·FFT/统计       │
└──────┬────────┘      └───────┬────────┘      └───────┬────────┘
       ▼                      ▼                       ▼
┌───────────────┐      ┌────────────────┐      ┌────────────────┐
│ 交互终端       │      │ 传统收发 + 文件   │      │ 绘图/统计仪表盘  │
│ Viewport(GUI) │      │ Viewport(GUI)  │      │ Viewport(GUI)  │
└───────────────┘      └────────────────┘      └────────────────┘
```

### 5.2 各引擎的独立解析管线

| 消费方 | 订阅内容 | 后台解析管线 | 产出 |
|--------|---------|------------|------|
| **交互终端** | 原始字节流 | ANSI 状态机 → 屏幕缓冲区 → SGR 染色（检测到 ANSI 时自动染色让位） | 带样式的屏幕网格 → 终端 Viewport |
| **传统收发** | 原始字节流 | 智能分包+时间戳 → 自动染色 → 过滤 | 带时间戳/颜色/过滤的日志行 → 日志 Viewport |
| **绘图** | 原始字节流 | 帧解析器（本地游标对齐）→ 通道分离 → 环形缓冲 | 通道采样 → 波形/柱状/FFT/统计 |
| **文件落盘** | 原始字节流 | 智能分包+时间戳（与日志共用规则）→ 编码转换 | 原始数据+时间戳 → 文件（含被过滤行，见 §1.4 待确认②） |

各管线的解析完全独立：改动 ANSI 引擎不影响绘图；时间戳分包只在日志/文件路径内生效，绘图永远拿到完整二进制帧。

### 5.3 线程模型

```
┌──────────────────────────────────────────────────────┐
│              Main Thread (GUI) - ~60 FPS              │
│  - DearPyGui 渲染循环                                  │
│  - 用户交互、键盘事件处理                               │
│  - 从各引擎的双缓冲读取最新快照 → 更新各 Viewport       │
│  - 绘图数据降采样 → push 到 Plot API                   │
└──────────────┬───────────────────────────────────────┘
               │
    ┌──────────┼──────────┬──────────┐
    ▼          ▼          ▼          ▼
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│  I/O   │ │ 终端引擎 │ │ 日志引擎 │ │ 绘图引擎 │
│ Thread │ │ 线程    │ │ 线程    │ │ 线程    │
│        │ │        │ │        │ │        │
│·串口读 │ │·ANSI   │ │·分包    │ │·帧解析  │
│·网络读 │ │ 解析   │ │·时间戳  │ │·通道分离 │
│        │ │·屏幕缓冲│ │·染色    │ │·FFT     │
│        │ │        │ │·过滤    │ │·统计    │
└────────┘ └────────┘ └────────┘ └────────┘
```

### 5.4 线程间通信

- **I/O Thread → 各引擎线程**：`queue.Queue`（线程安全），每个引擎一个队列，fan-out 时逐份拷贝
- **各引擎线程 → GUI Main Thread**：**双缓冲 + 帧同步**（每 ~16ms 交换一次，主线程只读快照）
- **Compute Pool → GUI**：`concurrent.futures` 回调（FFT/统计等重计算）

> **为什么不用 asyncio？** DearPyGui 的事件循环是原生 C++ 的，不能与 Python asyncio 直接整合。传统多线程模型更简单、更易调试。GIL 对 I/O 密集操作影响不大；各引擎解析本身是 CPU 密集，但受 GIL 限制无法并行——在 3.13 下吞吐已足够，若后续高速串口（12Mbps）暴露瓶颈，再按需把热点解析移到 C 扩展。

### 5.5 数据流速率估算

| 场景 | 数据速率 | 处理要求 |
|------|---------|---------|
| 典型调试串口 | 115200 bps ≈ 11.5 KB/s | 轻松 |
| 高速串口 | 3 Mbps ≈ 375 KB/s | 需注意 |
| 极限 USB CDC | 12 Mbps ≈ 1.5 MB/s | 需优化（降采样/丢弃策略） |

## 6. Project 系统设计

### 6.1 设计理念

一个 **Project** = 一个完整的调试工作环境快照。切换项目 = 一键恢复所有调试配置。

类比 IDE 的 Project 概念：你正在调试 STM32 板卡时有一套配置（串口、命令列表、绘图通道），切换到 ESP32 项目时需要另一套完全不同的配置。Project 文件让你在两者之间秒切。

### 6.2 .maxcomprj 文件格式

**方案：ZIP 压缩包，内含结构化文件。**

```
stm32_debug.maxcomprj  (本质上是一个 .zip)
│
├── project.toml            # 项目元数据 + 全局设置
├── transport.toml          # 传输/连接配置
├── commands.json           # 自定义命令列表
├── filters.toml            # 日志过滤规则
├── plots/                  # 绘图配置（可能有多个）
│   ├── sensor_wave.toml
│   └── motor_current.toml
├── view_state.toml         # UI 布局状态（窗口大小、面板显隐、当前激活视图）
└── history/                # 可选：历史数据
    └── (空，预留给后续)
```

```toml
[project]

[project.tags]
```

### 6.3 Project 生命周期

```
┌──────────┐    新建     ┌──────────────┐
│ 启动应用  │ ──────────→ │  空白项目     │
│          │             │ (默认配置)    │
└──────────┘             └──────┬───────┘
       │                        │
       │ 打开 .maxcomprj        │ 用户配置各种设置
       ▼                        ▼
┌──────────────┐         ┌──────────────┐
│ 恢复项目      │         │ 工作状态      │
│ (加载所有配置) │         │ (运行时修改)  │
└──────┬───────┘         └──────┬───────┘
       │                        │
       │                        │ Ctrl+S / 自动保存
       │                        ▼
       │                 ┌──────────────┐
       └─────────────────│  保存项目     │
```

- `新建项目` → 空白模板，选择传输方式 → 开始使用

- `另存为` → 保存为新文件

### 6.4 与全局配置的关系

```
全局配置 (用户级别)               项目配置 (.maxcomprj)
─────────────────────────        ─────────────────────
%APPDATA%/MAXCOM/                每个项目独立
├── config.toml        ← 全局    xxx.maxcomprj/
│   - 主题                  │    ├── project.toml
│   - 语言                  │    ├── transport.toml   ← 连接相关
│   - 字体                  │    ├── commands.json    ← 调试相关
│   - 默认编码              │    ├── filters.toml     ← 调试相关
│   - 最近项目列表          │    ├── plots/           ← 调试相关
│   - 端口黑名单            │    └── view_state.toml  ← 布局相关
│                           │
│  优先级: 低                │   优先级: 高 (覆盖全局)
└───────────────────────────┘
```

- 全局配置：和项目无关的个人偏好（主题、语言、字体）
- 项目配置：和特定调试任务绑定的设置（连接参数、命令列表、绘图）
- 冲突时：项目配置覆盖全局配置

```yaml
    branches: [main, dev]
  pull_request:
    branches: [main]

jobs:
  lint:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - uses: actions/setup-python@v5
        with: { python-version: "3.13" }
      - run: uv pip install ruff
      - run: ruff check src/ tests/

  test:
    runs-on: windows-latest
    strategy:
      matrix:
        python-version: ["3.13"]
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - uses: actions/setup-python@v5
        with: { python-version: "${{ matrix.python-version }}" }
      - run: uv sync --dev
      - run: uv run pytest tests/ -v --cov=src/ --cov-report=term-missing

  build:
    needs: [lint, test]
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - uses: actions/setup-python@v5
        with: { python-version: "3.13" }
      - run: uv pip install nuitka
      - run: uv run python -m nuitka --standalone main.py
      - uses: actions/upload-artifact@v4
        with:
          name: maxcom-windows
          path: main.dist/
```

### 8.2 测试策略

| 层级 | 范围 | 工具 | 目标覆盖率 |
|------|------|------|-----------|

- 使用 `com0com` 创建虚拟串口对（如 COM10 ↔ COM11）
- 测试时一端写入、一端读取，验证收发一致性
- CI 中用 PowerShell 脚本自动安装 `com0com`
