# ADR-0022: 收发区方向标记 —— 方向随字节走（总线载荷带标签），显示偏好留在前端

- 状态：**accepted**
- 日期：2026-10-12
- 裁决人：项目负责人（口头指令：「在开启回显后，希望在收发模式的时间戳之后加入 ←→ 表示收发。
  可以在设置页面控制开关，默认开」；并就"什么条件下显示"明确选择：**回显开启时才显示**）
- Supersedes：无
- 关联：ADR-0015（单一原始流扇出，本 ADR 只给其载荷加方向标签，不改其结论）、
  ADR-0021（`IoDir` 与 `read_io`）、SPEC `03-modules/logview`

## 背景

「本地回显」（`SendPayload.echo`）是为设备不回显的场景准备的：发送后把本机发出的字节
**按「到达」喂进同一条日志管线**，于是收发区能看见自己发了什么（引擎侧
`bus.publish_to("log", &bytes, IoDir::Tx)`）。

代价是**两种来源的字节在同一条管线上彻底同形**：

- 都经同一个 `LineSplitter` / 同一个解码器 / 同一个染色与过滤引擎；
- `ts_ms` 都是「本条字节到达日志线程的时刻」，`text` / `raw_hex` 也只由字节本身决定。

也就是说，**日志管线里没有任何一处保留"这行是谁发的"**。回显一开，界面上自己发的行
与设备回的行长得一模一样 —— 分不清，就只能拿"这条内容像不像我发的"去猜。

### 为什么不在前端猜

前端确实知道自己在某一刻发过什么，但以下每一条都能让"按内容/时刻匹配"失效：

1. **合并**：line 分包下空闲封行会把未结束的残余与后续字节合并进同一行，行的时间戳取
   **最后一次**活动时刻 —— 前端记录的发送时刻与行的 `ts_ms` 没有可对齐的关系。
2. **拆分**：`PARTIAL_FLUSH_CAP` 长流防护会把一行切成多条 entry。
3. **重编码**：解码器（gbk/auto）+ ANSI 剥离后，行文本未必等于发出的字节。
4. **同形内容**：命令与其回读常常逐字相同（`AT` → 设备回 `AT`），仅靠内容无从区分。

因此方向必须在**字节入队的那一刻**被贴上，并随字节一路走到 DTO。

## 决策

### 1. 方向作为事实，随总线载荷传播

`maxcom_core::bus` 的订阅载荷由 `Vec<u8>` 改为 `Chunk { bytes, dir }`（`Dir` = `rx` / `tx`），
并新增 `Dir` / `Chunk` 与 `publish_as`；`publish_to` 增加显式方向参数（其唯一调用点就是回显）。

| 方案 | 取舍 |
|---|---|
| **载荷带方向（选定）** | 方向与字节同批入队，**到达顺序严格保真**；下游（日志/绘图）各自决定是否关心。代价：core 的公开载荷类型变了一次，两个订阅点 + 测试要跟着改。 |
| 回显改投另一个主题（如 `"log-tx"`），方向由主题隐含 | 总线一行不改。但两个 channel 之间的先后由 `select!` 的就绪顺序决定 —— 同一瞬间的收发行可能被交换，而收发区恰恰是最能看出"顺序反了"的地方。弃。 |
| 在日志线程里按"最近一次 send"打标 | 发送与回显之间隔着写链路与异步 channel，判定必然靠时间窗猜；再叠加上面的合并/拆分，等于把不确定性搬进引擎。弃。 |

### 2. `IoDir` 与 `Dir` 合一（单一事实源）

引擎的 `IoDir`（MCP `read_io` 的收发区分）与总线方向是**同一件事**。若不合并，就必须在
`publish_to` 处 `IoDir → Dir` 转换，而任何一次漏转都表现为"标记反了"这种极难察觉的错。

做法：`Dir` 定义在 `maxcom_core::bus`（core 是两层共同依赖），引擎侧
`pub use maxcom_core::bus::Dir as IoDir;` 保留既有调用点与 MCP 的 `use maxcom_engine::session::IoDir`
不变。`Dir` 派生 `Serialize/Deserialize` 且 `#[serde(rename_all = "lowercase")]`
（取值 `"rx"` / `"tx"`，与 MCP `read_io` 的 `dir` 字面一致），`Default = Rx`。

### 3. DTO：`LogEntryDto.dir` 缺省即 `rx`

```rust
#[serde(default)]
pub dir: IoDir,
```

- 缺省 `rx`：老前端、老快照、不关心方向的消费者都按"接收"渲染，向后兼容；
- 语义只有两个取值，**不引入第三态**（"未知"与"接收"在界面上的表现本就该一致）。

方向在日志线程里逐一贴标：随每个收到的 chunk 更新 `cur_dir`，**空闲封行 / 停止收尾**产出的
条目沿用最后一次方向 —— 那些被刷出的缓冲字节正是它喂进来的（time 分包下若不沿用，
回显行会被误标成接收）。

### 4. 前端：方向随行存储，标记是纯渲染开关

- `LogViewPage.Row` 增 `dir`，**入队时随行存储**（与 `tsText` 同样的道理：数据层是事实，
  开关只是显示偏好，来回切不该丢信息）。`partial` 续行沿用首段的方向。
- `setDirMark(on)` 只重渲染已挂载的 chunk，不重建窗口 —— 避免把滚动位置一并重置。
- 标记紧跟时间戳之后、正文之前，`.log-dir` 定宽 `2ch`：有无标记的行内容列都对齐。

### 5. 可见性 = 设置页开关 ∧ 本标签页「本地回显」（本轮裁决）

- **设置页开关**（`settings.logDirMark`，默认**开**，`localStorage` 持久化，沿用项目既有的
  前端设置模式）：用户要不要这个标记。
- **叠加本地回显**：回显关闭时日志里只有接收行，标一列 ← 属于纯噪声。换言之，
  设置管"要不要用"，回显管"有没有必要用"。
- 两者都在变（全局设置广播 + 每标签页复选框），故收敛到 `SessionApp.syncDirMark()` 一处判断，
  避免两个入口各写一份而漂移。

**为什么不做"只标发送行"**：那样接收行不占位就无需定宽列，代价是内容列在收发行之间
左右跳动 —— 视觉稳定性比省两个字符重要。

**浮动日志窗口（popup）不标**：它是只读浮窗，没有发送面板也就没有本地回显，按同一条
"设置 ∧ 回显"规则天然为关 —— 不是漏做（`LogViewPage` 默认 `dirMark = false`，
谁都不主动开就不渲染）。

### 6. 导出：保存历史跟随窗口，捕获日志保持原格式

- `historyText()`（「保存历史」）的既有契约是"内容等同当前窗口"，故**同步带标记**。
- 「捕获日志」（`LogCapture`）的格式是"时间戳前缀 + 文本"的**文件格式**，已被用户脚本消费；
  本次**不加方向列**，以免悄悄改变既有解析。需要时另开一次决策。

## 后果

- 正面：
  - 收发区能可靠区分设备回读与本机回显，且**依据是事实而非启发式**；同形内容（`AT` → `AT`）
    也能一眼分开。
  - 方向随字节走，日志/绘图/后端各自取用：绘图线程另加了 `dir != Rx → skip` 的显式守卫，
    不再依赖"本地回显只投 log 主题"这一隐式前提。
  - `IoDir`/`Dir` 合一后，"方向"在整个仓库只有一个类型。
- 负面 / 风险：
  - 改动触及 core 的公开载荷类型（`Bus` 的订阅端返回 `Chunk` 而非 `Vec<u8>`）：任何未来的
    新订阅者都要处理方向；换主题方案本可让这个代价为零（但换来顺序不确定性，见上表）。
  - 标记列占用约 2ch 宽度，`无时间戳 + 字号极小`时是最不划算的组合（仍是纯显示项，可关）。
  - 回显开着时"自己发的行"会同时进日志与统计（既有行为，未改）。
- 未纳入：
  - 不做字形/颜色可配（←/→ 已由用户指定）；
  - 不在「捕获日志」里加方向列（见 6）；
  - 不把方向标记作为 MCP 工具暴露（它是显示偏好，不是数据能力；AI 读方向走 `read_io` 的 `dir`）。

  `local_echo_shows_sent_text_when_device_silent`（回显行必须 `dir == Tx`）、

- `app/scripts/log-echo-test.mjs`：设置开关默认开 + 端到端联动（回显关 → 无标记；
  回显开 → 接收行 ←、发送行 →）。
