### 1.2 终端显示引擎（Terminal Viewport）

这是整个项目**技术难度最高的模块**，需要实现一个完整的虚拟终端。

| 需求 | 优先级 | 说明 |

| 真彩色支持 | P0 | 24-bit color（`\x1b[38;2;R;G;Bm`） |
| Linux Shell 颜色格式 | P0 | 兼容 `\x1b[...m` 全部常用格式 |
| 等宽字体 | P0 | 用户可选字体、字号 |
| 语法高亮 | P1 | 类似 Rich 库 console 效果，支持自定义规则 |
| 日志等级过滤 | P0 | 自定义正则匹配规则（如 `\[D\]` `\[I\]` `\[W\]` `\[E\]`），可单独开关显示 |
| 多页签 | P1 | 多个终端视图并存 |
| 搜索/高亮 | P1 | 在接收区搜索关键字并高亮 |
| 自动换行 | P0 | 长行自动折行，可切换 |

**ANSI 解析核心能力：**
```
SGR: 颜色(16色+256色+真彩色)、粗体、斜体、下划线、删除线、反色、隐藏
光标: 上/下/左/右/行首/列定位/保存位置/恢复位置
编辑: 插入行(DEL)/删除行(IL)/删除字符(DCH)/擦除字符(ECH)
滚动: 设置滚动区域 + 上滚/下滚 → 实现"原地刷新"不滚屏
```

### 1.3 时间戳系统

| 需求 | 优先级 | 说明 |
|------|--------|------|
| 空闲分包超时 | P0 | 用户可配置空闲时间（如 50ms），超时后新数据视为新帧，附加新时间戳 |
| 时间戳格式可选 | P0 | 绝对时间 `HH:MM:SS.ms` / 相对时间 `+ms` / 差值 `Δms` |
| 时间戳与数据绑定存储 | P0 | 保存到文件时一并写入 |
| 按行/按帧模式切换 | P0 | 按行时间戳 vs 按空闲分包时间戳 |

**智能分包逻辑：**
```
数据到达 → 追加到当前帧缓冲区 → 重置空闲计时器
空闲超时触发 → 当前帧封包 → 附加时间戳 → 分发到显示/文件/绘图
新数据到达 → 开始新帧
```
这样即使 `printf` 被底层拆成多个 USB 包，只要空闲间隔 < 阈值，时间戳就不会被截断。

## 3. 技术选型讨论

### 3.1 GUI 框架：DearPyGui vs 备选

| 维度 | DearPyGui | PySide6/Qt | wxPython |
|------|-----------|------------|----------|
| 渲染性能 | ⭐⭐⭐⭐⭐ GPU 加速 | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| 实时数据刷新 | 极佳（原生为游戏/工具设计） | 良好 | 一般 |
| 绘图能力 | 内置 plot API | 需额外库(pyqtgraph) | 需额外库 |
| 控件丰富度 | 中等 | 极丰富 | 丰富 |
| 文档/社区 | 一般 | 极好 | 良好 |
| 打包体积 | 小 | 大 (~50MB+) | 中等 |
| 样式自定义 | 有限 | 极灵活(QSS) | 中等 |
| 跨平台 | Win/Mac/Linux | Win/Mac/Linux | Win/Mac/Linux |

**建议：保持 DearPyGui**，理由：
- 这个项目的核心是**高频实时数据刷新**（终端日志 + 波形图），这正是 DearPyGui 的强项
- DearPyGui 的 plot API 原生支持高性能波形图，省去第三方库的集成复杂度
- 打包体积小，分发方便
- 对于缺少的控件（如高级文本编辑），可以通过自定义实现

**风险点和应对：**
- DearPyGui 的字体渲染对中文支持需要验证 → 选择合适的中文等宽字体（如 Sarasa Gothic / 更纱黑体）
- 复杂布局（如 dockable panels）在 DearPyGui 中需要手动实现 → 封装布局管理器
- DearPyGui 的 Text Widget 渲染大量文本时的性能 → 虚拟化渲染（只渲染可见行）

### 3.2 语言：纯 Python vs Rust + Python

| 方案 | 优点 | 缺点 |
|------|------|------|
| 纯 Python | 开发快、生态好、插件用 Python 写最简单 | GIL 限制、CPU 密集型任务慢 |
| Rust 核心 + Python GUI | 性能极致、无 GIL、内存安全 | 开发复杂度翻倍、插件系统割裂 |

**建议：纯 Python 起步，关键路径用 Cython/Rust 优化。**

关键路径指：
1. 高频串口数据接收（>2Mbps）→ `asyncio` + `pyserial-asyncio` 或直接用 `ctypes` 调用 Win32 API
2. ANSI 解析 → 纯 Python 状态机即可；实测 Python 解析 10MB/s 的 ANSI 流无压力
3. FFT 计算 → `numpy` + `scipy`（已高度优化的 C/Fortran 实现）
4. 绘图渲染 → DearPyGui 的 GPU 渲染本身就是 C++

### 3.3 关键依赖选型

| 功能 | 推荐库 | 备选 |
|------|--------|------|
| 串口通信 | `pyserial` | `pyserial-asyncio`（如果需要 asyncio） |
| TCP/UDP | 标准库 `asyncio` | `socket`（同步模式） |
| WINUSB | `pywinusb` | 自研 ctypes 封装 |
| HID | `hidapi` | `pywinusb` |
| FFT/DSP | `numpy` + `scipy` | `pyfftw`（性能更好但依赖重） |
| 配置管理 | `pydantic` + `pyyaml` | `tomli` |
| 插件系统 | `importlib.metadata` + `stevedore` | 自研简单版 |
| 打包/分发 | `nuitka`（编译为 .exe） | `pyinstaller` |
| ANSI 解析 | **自研状态机** | `ansi2html` (功能不足) |

## 4. 模块详细设计

### 4.1 ANSI 解析引擎（自研核心模块）

这是整个项目**最有技术含量**的模块。需要从零实现一个符合 ECMA-48 / ISO 6429 标准子集的 ANSI 转义序列解析器。

**设计方案：状态机 + 虚拟屏幕缓冲区**

```
输入字节流
    │
    ▼
┌──────────────────────┐
│   ANSI Parser FSM    │
│                      │
│  States:             │
│   GROUND → ESCAPE    │
│         → CSI_ENTRY  │
│         → CSI_PARAM  │
│         → CSI_IGM    │  (intermediate)
│         → OSC_STRING │
│         → DCS_ENTRY  │
│         → SOS/PM/APC │
└──────────┬───────────┘
           │ events: Print(char), CursorMove, EraseInDisplay, Scroll, ...
           ▼
┌──────────────────────┐
│   Screen Buffer      │
│                      │
│   ┌────────────────┐ │
│   │  Line[0..N]    │ │  ← 每行存储 [(char, style), ...]
│   │  + SGR attrs   │ │
│   ├────────────────┤ │
│   │  Scrollback    │ │  ← 回滚缓冲区（可配置行数）
│   │  (环形缓冲)     │ │
│   └────────────────┘ │
│                      │
│   Cursor state:      │
│    - row, col        │
│    - saved_row/col   │
│    - visible         │
│    - scroll_region   │
└──────────┬───────────┘
           │
           ▼
    GUI 渲染层（DearPyGui Text / DrawList）
```

**需要支持的 ANSI 序列清单（核心子集）：**

```
CSI n m          SGR - 图形渲染（颜色、粗体、斜体等）
CSI n A/B/C/D   光标上/下/右/左
CSI n G         光标水平定位
CSI n;m H/f     光标行/列定位
CSI s/u         保存/恢复光标位置
CSI ?25 h/l     显示/隐藏光标
CSI 2 J         清屏
CSI K           清除行
CSI n L/M       插入/删除行
CSI n P         删除字符
CSI n @         插入字符
CSI n;m r       设置滚动区域
CSI 6 n         获取光标位置（响应）
ESC 7/8         保存/恢复光标+属性（DEC 兼容）
```

**性能优化思路：**
- 状态机用查表法而非大量 if/else
- 屏幕缓冲区使用行级脏标记，只重绘变更的行
- 回滚缓冲区使用环形队列，避免大量内存分配
- 长行（>10000字符）使用虚拟化渲染，只渲染可见部分

    @abstractmethod

    @abstractmethod

    @abstractmethod

    # 控制
    @abstractmethod
    def get_config(self) -> TransportConfig: ...
    @abstractmethod

    # 事件

    on_error: Callable[[Exception], None]

## 5. 数据流与线程模型

### 5.1 线程模型（关键设计决策）

```
┌─────────────────────────────────────────────────────────┐
│                    Main Thread (GUI)                      │
│  - DearPyGui 渲染循环 (~60 FPS)                          │
│  - 用户交互处理                                           │
│  - 从共享缓冲区读取数据更新显示                            │
│  - 绘图数据降采样后 push 到 Plot API                       │
└──────────────────────┬──────────────────────────────────┘
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
    ┌──────────┐ ┌──────────┐ ┌──────────┐
    │ I/O      │ │ Pipeline │ │ Compute  │
    │ Thread   │ │ Thread   │ │ Pool     │
    │          │ │          │ │          │
    │ - 串口读 │ │ - ANSI   │ │ - FFT    │
    │ - 网络读 │ │   解析   │ │ - 统计   │
    │ - 时间戳 │ │ - 过滤   │ │ - 大文件 │
    │          │ │ - 帧解析 │ │   操作   │
    └──────────┘ └──────────┘ └──────────┘
```

**线程间通信：**
- I/O Thread → Pipeline Thread：`queue.Queue` (线程安全)
- Pipeline Thread → GUI Main Thread：双缓冲 + 帧同步（每隔 ~16ms 交换一次）
- Compute Pool → GUI：`concurrent.futures` 回调

**为什么不用 asyncio？**
- DearPyGui 的事件循环是 Native C++ 的，不能与 Python asyncio 直接整合
- 用传统多线程模型更简单、更容易调试
- Python GIL 对 I/O 密集操作（串口读写）影响不大

### 5.2 数据流速率估算

| 场景 | 数据速率 | 处理要求 |
|------|---------|---------|
| 典型调试串口 | 115200 bps ≈ 11.5 KB/s | 轻松 |
| 高速串口 | 3 Mbps ≈ 375 KB/s | 注意 |
| 极限 USB CDC | 12 Mbps ≈ 1.5 MB/s | 需要优化 |

对于 375 KB/s 的持续数据流，Pipeline Thread 每毫秒约需处理 375 字节——纯 Python 的 ANSI 解析完全足够。GUI 只需要渲染当前可见行（~50行），不需要渲染全部历史数据。

## 8. 待讨论问题

### 🤔 讨论 1：ANSI 解析器——自研 vs 移植？

自研的好处是完全可控，但要实现完整的 VT100/xterm 兼容需要很大工作量。
**我的建议**：自研核心子集（SGR + 光标移动 + 滚动 + 清屏），覆盖 90% 的实际使用场景。遇到不支持的序列，记录日志但不崩溃。后续再逐步补全。

你怎么看？需要覆盖到什么程度？

### 🤔 讨论 2：DearPyGui 的 terminal widget 实现方案？

DearPyGui 没有原生的 terminal widget。有两个方案：

**方案 A**：用 `draw_text()` + `draw_rect()` 逐行绘制。优点是完全控制，缺点是开发量大。
**方案 B**：用 `add_text()` 或 `add_input_text_multiline()` 只更新变化的部分。优点是简单，缺点是字体颜色/样式可能受限。

**我倾向方案 A**，因为 ANSI 颜色/样式是核心需求。

### 🤔 讨论 3：是否需要支持脚本扩展？

类似 SecureCRT 的脚本功能（Python/Lua），允许用户写脚本自动化操作。
好处是灵活性极大，代价是实现复杂度高。

**我的建议**：Phase 4 再做，且只支持 Python 脚本（因为整个应用本身就是 Python）。

### 🤔 讨论 4：配置文件格式？

- JSON：简单，无依赖，但不能写注释
- YAML：可读性好，支持注释，但缩进敏感
- TOML：可读性好，有类型，Python 3.11+ 内置支持

**我倾向 TOML**，用于会话/配置文件，命令列表可以用 JSON（便于导出交换）。

### 🤔 讨论 5：是否需要 Web 版本？

Web 版本（通过 WebSerial API）可以跨平台运行，但性能和功能受限（无法访问 WINUSB/HID，无法做本地文件操作）。

**我的建议**：先做好桌面版，架构上保持核心层与 GUI 层解耦，未来如果要做 Web 版只需替换 GUI 层。

### 🤔 讨论 6：项目命名

"FXX-MAXCOM" 作为代号还行，但正式名称你有想法吗？一些建议：
- **MaxLink** — 极致连接
- **DeepCOM** — 深度串口
- **OmniTerm** — 全能终端
- 或者保留 **MAXCOM**
